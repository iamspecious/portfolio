You Can't Presume Context: A First Run of PostHog, Documented Live

Installed PostHog cold on this site, documented seven findings live, filed four issues and a docs PR — the write-up.

Specious Coda Bishop · July 2026

I installed PostHog on my portfolio site this week — a plain HTML static site on GitHub Pages. I went in as a genuine first-time user, and I wrote down everything that happened while it happened. By the end I'd filed four issues and a docs PR. This is the story of that first hour, and what it taught me about first-contact design.

The wizard assumed things about me

The docs routed me to the install wizard. What's interesting is that it doesn't state it needed to be run in terminal to begin with. And once you're in, the terminal thing itself doesn't allow you to back out — it wants you to pick a framework. My site doesn't have a framework. The picker had no option for that, and no exit.

"Oh well, our users should know to open terminal." No — they're not going to. This is your first time using the platform; you can't presume knowledge. Or more precisely: you can't presume context. A senior engineer doesn't know your wizard's conventions on first contact either. The sin isn't assuming technical skill — it's assuming familiarity nobody has yet.

  • Filed: PostHog/wizard#870 — no path for static sites

"Web" doesn't mean what you think it means

My correct path turned out to be the JS snippet — a single paste into the head. It technically lives behind the "Web" tile in the SDK grid. But if I see "Web" I think React, JavaScript, Java — something more technical — not "here's the JS snippet you need for your HTML." Every option in that grid is the web. The label only makes sense once you already know the SDK taxonomy, which is exactly the person who doesn't need the signpost.

And "set up manually" is ambiguous depending on where you are on the technical ladder. For some people it means running and configuring in a terminal; for others it means manually placing a snippet into existing HTML. Same words, different users, different meanings.

  • Filed: PostHog/posthog.com#18390 — a docs PR routing static sites to the snippet at the exact moment they've scanned the frameworks list and found nothing.

A funnel drop-off inside the funnel company

Connecting GitHub as a data source: I authorized on GitHub's side and got redirected... back to the connection screen I started on. No indication whether it worked or not. And the task was abandoned midway — if you're already in the process of connecting GitHub, why would you be redirected somewhere that isn't GitHub? Surely you'd want to select your repos, then be prompted to connect other things.

PostHog's core product detects funnel drop-off. This is a textbook funnel break — a step where the user exits an in-progress task with no completion state — inside the onboarding of the funnel-analytics company. The exact pattern their own product exists to catch.

  • Filed: PostHog/posthog#70206 — OAuth redirect drops the task with no success state

To be fair — and this matters — once you're back inside the GitHub connection the second time, the webhook setup and the explainers of where to go and what to do were great. The capability for good guidance clearly exists. These are gaps in coverage, not competence.

The theme: silent states

The same defect kept recurring in different clothes. The OAuth redirect gave no success state. The Quick start checklist tracks progress fine, but the button vanishes from the top bar mid-flow — if you save on the page you're configuring and it doesn't populate, and you're mid-flow, it breaks that flow.

  • Filed: PostHog/posthog#70204 — Quick start button disappears mid-flow

And at the very end, with the snippet deployed and events flowing, my honest reaction was "from what I can tell, it works?" — success inferred from seeing myself in the data, never announced.

Every action a user takes should return a legible state change. Silence after an action is indistinguishable from failure — so users retry, duplicate, or leave.

The choices I made on my side

I put PostHog on the EU cloud and set person_profiles: 'identified_only' — anonymous visitors are tracked without a full person profile being created, and a profile only forms once someone takes an identifying action. For a portfolio site serving EU visitors, that felt like the right starting default: less identity data captured by default, not more.

And the reason I wanted analytics at all: I'm job hunting, and I want to know whether application reviewers actually open the portfolio, which pages they read, and how long they stay. This isn't vanity instrumentation — it's my own funnel.

What I took from it

Deliver the right information at the moment of need, rather than making people hunt for it. Regardless of your literacy or technical level, these first touch points matter. Most people will dig through the docs — but can't we make it easier? Give it to them up front?

That's the whole thesis. It's also, I'd argue, the whole job of docs, onboarding, and context engineering: knowledge moved to the point of first contact, for humans and agents alike — because neither reads the manual before acting.
